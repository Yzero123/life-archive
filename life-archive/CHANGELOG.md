# 版本历史

本文件记录**每一个版本改了什么、为什么改、怎么回退**。

每个版本都有三样东西：

| 东西 | 位置 | 用途 |
|---|---|---|
| Git tag | `v1.x.y` | 源码级回退：`git checkout v1.x.y` |
| GitHub Release | <https://github.com/Yzero123/life-archive/releases> | 下载任意历史版本的安装包 |
| 安装包 zip | `releases/life-archive-<版本>.zip` | 直接在 MCode 里安装 |

> **怎么回退**（三种，按场景选）：

```bash
# 1. 只想要某个旧版的安装包 → GitHub Releases 页面下载对应 zip，重新安装
#    https://github.com/Yzero123/life-archive/releases

# 2. 想把源码切回某个版本（改代码、做对比）
git clone https://github.com/Yzero123/life-archive.git
cd life-archive
git checkout v1.6.2          # 切到旧版
git checkout main            # 切回来

# 3. 想把仓库整体回退到某个版本（谨慎，会改写历史）
git revert <commit-sha>      # 逐个撤销
```

### 为什么升大版本

插件 ID 变了 = **对已安装的用户是破坏性变更**：

- 数据目录名变了，旧数据不会自动跟过去（迁移方法见下）；
- MCP 工具前缀变了（`mcp__qq-space-kb__kb_search` → `mcp__life-archive__kb_search`）；
- 技能名、子代理名都变了，委派时要改引用。

功能本身**一行没改**——这版只做身份与文档的重命名。

### 数据迁移

```bash

mv ~/.minimax/plugins/qq-space-kb ~/.minimax/plugins/life-archive

mv ~/.minimax/v2/plugin-data/liveboards/qq-space-kb \
   ~/.minimax/v2/plugin-data/liveboards/life-archive
```

> 数据目录里只有**本机的个人数据**（QQ 空间导出、朋友圈导出、已建的知识库），
> 它从来就不进安装包、不进 Git 仓库。换目录名不影响任何一条记录。

按用户决定，**保留完整 git 历史**（旧 tag 与旧 Release 仍可回退）。

## v2.1.0 — 2026-10-23

**朋友圈互动扩展：你在别人朋友圈下留的言、给别人点过的赞，也进知识库了。**

2.0 只收「你自己发的朋友圈」。但一个人在网上留下的痕迹不止动态——
**在别人朋友圈下留的言**、**给别人点过的赞**，同样是「过去的你」。

### 新增能力

| 记录类型 | id 前缀 | 来源标记 | 本机实测条数 |
|---|---|---|---|
| 本人发的动态 | `wx-` | `wechat-sns` | 255（2015-04-13 → 2026-10-22） |
| **我的留言** | `wx-c-` | `wechat-sns-comment` | **925**（848 条是回复自己动态下的人，77 条是评论好友动态） |
| **我的点赞** | `wx-l-` | `wechat-sns-like` | **101** |

### 最重要的一条：好友的原文永远不进「我说的话」

| 记录类型 | `user_voice` | 接地校验 | 表达习惯 | 年份分布 |
|---|---|---|---|---|
| 本人发的动态 | 全文 | ✅ | ✅ | ✅ |
| **我的留言** | **只有我的原话** | ✅ | ✅ | ✅ |
| **我的点赞** | 空 | 只作事实 | ❌ | ❌ |

好友原文会以「上下文」形式留在留言记录的正文里（截断 60 字，单独放在 `raw.reply_snippet`），
但**不会**进入接地校验、**不会**进入表达习惯统计。

> 为什么这么严：接地校验是拿「模型说的话」去比对「我说过的话」。
> 好友原文一旦混进去，bot 就会把**别人说过的话**当成我说的——
> 口头禅、语气全被污染，而且这个错误**看不出来**（回答读着很顺，但不像你）。

### 新增的画像维度

发圈类维度（节奏 / 时段 / 媒体 / 类型 / 位置 / 互动最多的人）**只算本人发的动态**。
互动类维度单独成组：

| 维度 | 含义 |
|---|---|
| `[朋友圈·我的互动]` | 留言多少条、点赞多少次 |
| `[朋友圈·最常回复的人]` | 我最常回复谁（**排除**自己动态下的回复） |
| `[朋友圈·留言风格]` | 平均每条几字、我的高频词、最常在什么时段留言 |
| `[朋友圈·收到的反馈]` | 我的动态收到了多少赞、多少评论 |

### 取数：互动数据只能自己导

工具的 `POST /api/sns/exports` **会丢掉 `like_user_list`**（导出的 likes 恒为空），
而且导出时把「我回复别人」的评论者昵称填成我自己的昵称，分不出哪条是我的。

→ 互动数据**必须**用本插件自带的 `wx-export-runner.py --scope all` 导（读已解密快照，不经过工具导出层）。
取法见《微信朋友圈取数操作指引》§4.4。

### 顺带修掉的三个坑

1. **「我回复自己朋友圈下的人」被本人分支吞掉**——实测 848 条留言全在自己发的动态下面。
   处理顺序改成**先处理我的留言、再处理本人动态**。
2. **微信在「我回复别人」时把评论者昵称填成我自己昵称**——于是「互动最多的人」第一名永远是我自己
   （实测 850 次里 848 次是自己）。判定「是不是我」一律用 `username` 比对（并剥掉设备后缀），**不靠昵称**。
3. **微信生成的 XML 有裸 `&` 不转义**（公众号链接里的 `&mid=` `&idx=` `&sn=`），
   标准 XML 解析器直接判 not well-formed——本机 1067 行里 **378 行**栽在这上面，
   且几乎都是**内容最值得留**的那些。runner 里先做 `&` 归一化，修完 **1067 行全部解析成功，0 失败**。

### 面板与开关

- 导入**整个目录**并按动态 id 合并（之前只挑「本人发的那一份」，会把好友文件里的我的留言丢掉）。
- 落盘最小化：raw 只留「本人发的 + 我互动过的」。
- 状态栏三段式计数：**N 条动态 · M 条留言 · K 次点赞**。
- 新增「**关闭朋友圈互动**」开关：关掉后**留言与点赞一条都不入库**，行为与 2.0.7 一致。
- 新增 `POST /api/wx/interactions`。

### 隐私回扫的一次自撞修复

2.1 把**自己拼的模板文案**（「【留言】在…下留言」）写进了知识库，
而回扫器正是拿知识库当指纹源——于是**回扫器扫包时撞上了包里的同一段模板**，自己告自己。

修法不是放宽标准，而是**把指纹源改对**：指纹只取**来源内容**
（我的原话 `user_voice`、好友原文 `reply_snippet`、QQ 空间原文），不取**我们自己写的模板文案**。
并给回扫器补了**正/反样本自检**：正样本（真实文本片段、真实昵称）必须抓得住，反样本（自己的模板）必须抓不住。

### 顺带修掉的两个真问题

1. **MCP 把知识库永久缓存住了。**
   MCP 服务器是**常驻进程**，早期版本把知识库读进内存就再也不管。
   于是「导入新数据 → 重新构建知识库」之后，问 bot 拿到的还是**重建之前**的旧画像
   （实测 `kb_profile` 仍返回旧的 `updatedAt`，「最常回复的人」还停在我自己）。
   → 改成按**文件 mtime + 大小**判断：文件变了就重读。
   并补了专项回归 `tests/mcp-cache.mjs`（临时知识库 + 改文件 + 验读到的确实是新内容）。

2. **「条数」在三处对不上。**
   `[跨度]` 说 1371 条、`[年份分布]` 加起来 1270、`kb_stats` 的年份分布又是 1371——
   三个地方都叫「条数」，数字却不一样，模型和看板会互相打架。
   → 统一成：**所有记录都算条数**（点赞也算，它确实发生在某一年里），
   只有「我说的」才进表达习惯、话题、代表性内容。

### 不受影响的部分

- 1.0 **逐字节黄金基线**未破（`tests/test.mjs` 121 项全过）。
- 2.0 的朋友圈解析结果**逐字段未变**：`myComments` 为空时行为与 2.0.7 完全一致。
- 朋友圈关闭时，一切与 2.0.7 相同。

### 测试

| 套件 | 结果 |
|---|---|
| `tests/test.mjs` | 121 通过 / 0 失败（1.0 黄金基线） |
| `tests/test-wx.mjs` | 89 通过 / 0 失败（含新增的 [7] 朋友圈互动 13 项） |
| `tests/privacy-scan.mjs` | 27 通过 / 0 失败（含新增的正/反样本自检 4 项） |
| `tests/mcp-cache.mjs` | 5 通过 / 0 失败（新增：缓存随文件失效） |
| 其余套件 | 全过 |

## v2.0.7 — 2026-10-23

**多次导入改成「合并」，让滑动的缓存窗口能一点一点攒成历史；并补齐「怎么才能拿到全量」的完整路线。**

### 改的代码（一处行为变更）

`POST /api/wx/import` 之前是**覆盖**写 `raw/wechat_sns.json`，现在是**按动态 id 合并**。

| 情况 | 之前 | 现在 |
|---|---|---|
| 新导出里有旧数据没有的动态 | 加进去 | 加进去（一样） |
| 新导出里没有旧数据里的动态（缓存窗口滑走了） | **被抹掉** | **保留** |
| 同一条动态又出现（点赞数/评论变了） | 取新的 | 取后来的那份 |

**为什么要改**：朋友圈历史在微信服务端，本地 `sns.db` 只保留一个**会滑动的缓存窗口**。
覆盖的话，窗口滑走一次，之前攒下的就白攒了——历史永远攒不齐。
合并之后，每次导入只增不减，窗口滑到哪里就攒到哪里。

> 合并时按动态 id 去重；时间字段名不统一（`time` / `create_time` / `createTime` / `ts`），
> 排序键做了兼容处理。

### 新增工具

| 文件 | 位置 | 作用 |
|---|---|---|
| `wx-window-check.sh` | **仓库根 `tools/` 下**（不在安装包里） | 朋友圈本地窗口体检 + 增量检测：跑一次全量同步，打印快照行数、年份分布、本人条数与最早日期。**翻朋友圈之前跑一次当基线，翻完再跑一次对比** |

### 文档

## v2.0.5 — 2026-10-23

**修正朋友圈条数口径：5 条 → 34 条，并把「条数对不上怎么办」写进取数指引。**

上一版文档里写的「本机导入了 5 条微信朋友圈」是**首次导出的假象**，不是真实数据量。
真实情况是 **34 条**（2026-03-29 → 2026-10-22），知识库总量 **124 条**（QQ 空间 90 + 朋友圈 34）。

### 真因

WeChatDataAnalysis 的导出服务读的是**解密快照**里的 `SnsTimeLine`。
刚抓完密钥、快照还冷启动时，那张表里只写进了最新那几行 → 首次导出只有 5 条。
隔一会儿快照补齐后重导一次，就是完整的 34 条。**不是导出漏数据，也不是库被截断。**

### 这版改了什么

| 位置 | 改动 |
|---|---|
| 包内 CHANGELOG | v2.0.4 条目里的「5 条」改成「34 条」 |
| 仓库根 CHANGELOG | 端到端验收表：导出 5→34、双源画像 95→124、黄金基线口径同步更正 |
| 《微信朋友圈接入方案-2.0.md》 | §9.4 验收结果与「已知边界」同步更正；把「本地只有 5 条」的错误判断换成「导出条数偏少要先重导一次」 |
| 《微信朋友圈取数操作指引.md》 | 新增排查步骤：导出前先用 `/api/sns/timeline` 看真实条数，和导出的 `postCount` 对一下；对不上就重导 |

### 代码零改动

这版**只改文档**，包内 `miniapp/`、`mcp/`、`agents/`、`skills/` 一行代码没动，
测试与隐私回扫全量复跑仍全过（121 + 68 + 20 项）。

## v2.0.4 — 2026-10-23

**隐私回扫器修两处误报：语料变大后不再把通用汉语当泄漏，账号标识符不再被截成裸串。**

2.0.3 之后本机导入了微信朋友圈，真实语料一下子多了 34 条**带完整正文**的动态，
回扫器随即报出一堆「泄漏」——逐条查下来全是**误报**。

### 修的两处

| # | 现象 | 真因 | 修法 |
|---|---|---|---|
| 1 | 文档里的「什么样的」「实在不行」「恢复已删」被判成真实内容泄漏 | 中文滑窗是 **4 字**，语料一大就撞上到处都有的通用短语 | 滑窗改 **6 字**。成句的真实内容照样命中（已做正样本验证：注入 8 字真实片段，当场报警），通用短语不再误伤 |
| 2 | 文档里所有正常的 `wxid` 字样被判成账号标识符泄漏 | 账号标识符去掉设备后缀时，`wxid_<一串数字>` 这种「整串数字」的账号被截成裸串 `wxid` | 截出来的基名也要过「像不像标识符」的检查；退化值（太短、不含数字下划线）不当指纹 |

> 第 2 条其实是**门自己抓到了门**：改完之后，扫描器把我自己在注释里写下的
> 一个真实好友标识符当场报了出来——这说明这道门确实在干活。

## v1.7.0 — 2026-10-23

**对话模块重写：知识库整体当 prompt，交给宿主大模型。**

### 问题

用户反馈「对话模块太笨」。根因是**检索闸门**：检索没命中就根本不调模型，直接回固定话术。
问法一变就露馅——「我是个什么样的人」检索不到任何一条具体说说，于是 bot 只会说「当时的我还不知道这是什么意思」，
可知识库里明明有几十条有正文的记录，**它明明答得出来**。

### 改动

| 项 | 原来 | 现在 |
|---|---|---|
| 检索的角色 | 闸门：决定答不答得出来 | 只负责给模型**找资料** |
| 喂给模型的资料 | 命中的几块明细 | 分层：你是谁 + 人设 + 年度小结 + 相关说说（**落空时自动补全库速览**） |
| 固定话术由谁决定 | 代码判「检索不到」 | **模型自己说**——它手里有全库，说没有就是没有 |
| 措辞重合度 | 拒答闸门 | **不再拒答**，只展示 |
| 事实红线对照范围 | 本轮检索到的那几块 | **整个知识库** |

### 顺带修的

- **数字认写法也认区间**。模型把 `3261887` 写成「326 万」是四舍五入不是编造；
  中文里「五十多万」说的是区间（50 万到 60 万），库里有对应量级的数就算数。
  但库里随便一个「50」不能再给「50 万」背书——规则松了红线就形同虚设。
- **宿主报「暂时不可用」要重试**。宿主在 Mini App 刚启动 / 运行时换代的那一瞬间
  会回 `AGENT_UNAVAILABLE`，它的定义是「什么都没开始，稍后重试即可」。
  不重试的话，起来后问的**第一句话**会直接报错，第二句又正常，像「偶发抽风」。
- **提示词要求条数照年度小结抄**，不要自己数全库速览的行数——数出来的会错，错的会被红线拦下。
- MCP 的 `kb_ground_check` 与页面口径对齐（`ok` 不再受重合度影响）；
  技能第 2 步改成「检索没命中就用 `kb_records` 翻全库」。

### 验证

121 项测试全过；真实模型端到端四问全过（泛化问能答出有据的个性化回答、条数照年度小结答对、越界问题模型自己说不知道）。

| ① 导出 | 手机 QQ 扫码，Agent 驱动导出工具抓取全量说说 | `messages.json`（含评论/点赞/定位/图片）+ 归档库快照 |
| ② 建库 | 两路数据按说说 ID 合并去重，切明细块与年度画像块 | 可检索的知识库 + 检索索引 |
| ③ 人物画像 | 归纳时间线、社交圈、说话方式、性格 | 一份「我是谁」底色，注入每轮对话 |
| ④ 对话 | 检索 → 接地校验 → 作答 | 有依据的回答，附来源 |

工程要点：cell ID 前 8 位小端 u32 反解出作者 QQ 号（用于归属过滤），
后 8 位反解出精确发布时间戳；没正文也要留痕——「发过、什么时候发、被谁互动过」本身就是真实知识。
